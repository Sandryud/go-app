# Фоновые задачи (Asynq) и кеширование API

Документ дополняет [sessions-and-analytics-architecture.md](sessions-and-analytics-architecture.md): зафиксирован выбор **Asynq + Redis** для очередей и согласованная политика кеширования HTTP.

---

## 1. Зачем Asynq и Redis

- **Снять нагрузку с PostgreSQL:** расчёт итогового отчёта тренировки и обновление производных агрегатов не выполняются в запросе `POST .../complete`; служебные таблицы очереди на PG не используются.
- **Предсказуемые ответы API:** короткая транзакция (статус сессии, постановка задачи) и быстрый HTTP‑ответ.
- **Масштабирование:** воркеры Asynq можно запускать отдельными репликами; Redis — общая точка координации.

Зависимость инфраструктуры: **Redis** должен быть доступен API при завершении сессии (enqueue) и воркерам (consume).

---

## 2. Задачи, которые обрабатываются через Asynq

| Задача | Когда ставится в очередь | Что делает воркер |
|--------|---------------------------|-------------------|
| **`ComputeSessionReport`** | После успешного `POST /api/v1/sessions/:sessionId/complete` (и при принятом продуктовом решении — после `POST .../cancel`, если считается частичный отчёт) | Читает `workout_session_sets` и слоты; считает метрики; пишет `workout_session_reports`; выставляет `report_status`; при наличии таблицы — обновляет `plan_day_workout_stats` |
| **`InvalidateWorkoutsSummaryCache`** (опционально) | Из хвоста обработчика `ComputeSessionReport` или отдельной задачей с тем же `session_id` | Удаляет ключи Redis для `GET .../workouts-summary` по затронутому `plan_id` / `user_id` |
| **`RecomputePlanDayStats`** (опционально) | Если агрегаты по дням вынесены и требуют отдельного пересчёта | Синхронизация материализованной статистики по дню плана |

**Не используют Asynq:** создание сессии, лог подхода, замена упражнения, просмотр состояния — только синхронный путь через приложение и PostgreSQL.

**Идемпотентность:** повторная доставка `ComputeSessionReport` не должна дублировать бизнес‑эффект: перед записью проверять, что отчёт ещё не в состоянии `ready` (или использовать детерминированный upsert по `session_id`).

**Retry:** для `ComputeSessionReport` настроить разумный `MaxRetry` и backoff; при исчерпании — запись `report_status=failed` и `report_error` в БД (если предусмотрено схемой).

### 2.1 Глобальная история упражнения (`GET .../exercises/:exerciseId/performance-history`)

В SQL/репозитории учитывать только сессии со статусом **`completed`** и **`cancelled`**. Статус **`in_progress`** не включается (активная сессия — отдельные эндпоинты сессии). Подробнее: [sessions-and-analytics-architecture.md](sessions-and-analytics-architecture.md) («Зафиксированные продуктовые решения»).

## 3. Кеширование HTTP (Redis)

Кеш ответов API может жить в **том же Redis**, что и Asynq:

- Разделение: **префикс ключей** `cache:` (или аналог) и/или **отдельный DB index** Redis (`SELECT 1` для кеша, `0` для Asynq — уточнить в конфиге).
- Инвалидация предпочтительнее длинного TTL для данных, которые должны обновляться сразу после завершения тренировки.

### 3.1 Таблица решений по эндпоинтам

| Метод и путь | Кеш? | Рекомендация |
|--------------|------|----------------|
| `GET /api/v1/plans/:planId/workouts-summary` | **Да** | Ключ `cache:workouts_summary:{user_id}:{plan_id}`. Инвалидация при завершении/отмене сессии по этому плану (из воркера или синхронно после enqueue) **или** TTL 30–120 с как упрощение |
| `GET /api/v1/sessions/:sessionId/report` (готовый отчёт) | **Опционально** | Ключ `cache:session_report:{session_id}`; после `ready` данные неизменны — длинный TTL |
| `GET /api/v1/plans/:planId/days/:dayId/sessions/latest` | **Опционально** | Короткий TTL или инвалидация при старте/завершении сессии для этого дня |
| `GET /api/v1/sessions/:sessionId` | **Нет** | Активная тренировка — частые изменения |
| `GET /api/v1/sessions/:sessionId/slots/:slotId/performance-history` | **Нет** | Каждый подход меняет ответ |
| `GET /api/v1/exercises/:exerciseId/performance-history` | **По умолчанию нет** | При необходимости — только первая страница, короткий TTL; основной упор на индексы БД |
| `GET /api/v1/sessions/:sessionId/detail` | **Опционально** | Дублирует отчёт; часто достаточно не кешировать, если клиент использует `report` |

Мутации (`POST` сессии, подходы, `complete`, `cancel`) должны **инвалидировать** связанные ключи `workouts_summary` и при необходимости `sessions/latest` для затронутых `plan_id` / `day_id`.

## 4. Связь с кодом (ориентиры)

- Публикация задач: слой usecase после успешной фиксации транзакции завершения сессии.
- Обработчики Asynq: отдельный пакет, например `internal/worker/asynq` или `cmd/worker`.
- Абстракция `ReportJobPublisher` в домене/usecase позволяет подменить реализацию в тестах (mock без Redis).
